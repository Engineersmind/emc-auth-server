What this document is EMC Auth is your self-hosted Auth0 replacement. This guide walks you through the exact screens and API calls to set up Revi AI with three separate environments (revi-dev · revi-stage · revi-prod), each with their own isolated users, roles, and permissions — exactly like you would in Auth0.

Multi-Tenant Architecture for Revi AI

How tenants work in EMC Auth Each tenant is a completely isolated namespace. Users, roles, and permissions in revi-dev are invisible to revi-prod. Every API call includes an X-Tenant-Slug header so the server knows which tenant context to use.
🔵 revi-dev
  • Slug: revi-dev
  • Users: developers
  • Roles: dev-engineer, dev-admin
  • Permissions: feature:*, debug:*
  • API Keys: Revi app dev keys
🟠 revi-stage
  • Slug: revi-stage
  • Users: QA + PMs
  • Roles: qa-engineer, product-manager
  • Permissions: feature:read, test:*
  • API Keys: Revi app staging keys
🟢 revi-prod
  • Slug: revi-prod
  • Users: end users
  • Roles: user, premium-user, admin
  • Permissions: reply:read, reply:write
  • API Keys: Revi app production keys

Step-by-Step Setup Journey

Starting point Login as Super Admin at http://localhost:5173 with admin@emc.local / ChangeMe123!

Create the three Revi AI tenants

Go to Tenants in the nav → click + New Tenant → create each one:

Tenant 1 — Development
Name: Revi Dev  |  Slug: revi-dev
Tenant 2 — Staging
Name: Revi Stage  |  Slug: revi-stage
Tenant 3 — Production
Name: Revi Prod  |  Slug: revi-prod
Screen: /tenants → New Tenant button  |  API: POST /api/v1/admin/tenants (requires tenant:manage)

Open Revi Dev — create permissions

Click Manage on revi-dev → go to Permissions tab → add the permissions your app will check:

feature:read   feature:write   debug:access   admin:access
Screen: /tenants/:id → Permissions tab  |  API: POST /api/v1/admin/tenants/:tid/permissions

Create roles and assign permissions

In Revi Dev → Roles tab → create roles and pick which permissions each gets:

Role: dev-engineer
Permissions: feature:read, feature:write, debug:access
Role: dev-admin
Permissions: feature:read, feature:write, debug:access, admin:access
Screen: /tenants/:id → Roles tab  |  API: POST /api/v1/admin/tenants/:tid/roles

Add users to Revi Dev

In Revi Dev → Users tab → add each developer:

john@revi.ai   →   dev-engineer
shreyash@revi.ai → dev-admin
Screen: /tenants/:id → Users tab  |  API: POST /api/v1/admin/tenants/:tid/users

Repeat for Revi Stage and Revi Prod

Each environment gets its own isolated permissions, roles, and users. Changes in revi-dev have zero impact on revi-prod.

Tip: In Revi Prod keep permissions minimal (reply:read, reply:write). Add admin:access only to trusted prod admins.

Create an API key for each Revi environment

Go to API Keys → click + New API Key → one per Revi environment. Copy the raw key immediately — it is shown only once.

Key for revi-dev backend
emck_•••••••••••••••• (copy and set in Revi .env as EMC_API_KEY)
Screen: /api-keys  |  API: POST /api/v1/admin/api-keys
In Revi AI requests: send as Authorization: ApiKey emck_... or X-API-Key: emck_...

Users log in via Revi AI app

Revi AI frontend calls EMC Auth with the tenant slug in the header. EMC Auth validates credentials, returns JWT with permissions embedded.

Login request from revi-dev frontend
POST /api/v1/auth/session
X-Tenant-Slug: revi-dev
{ "email": "john@revi.ai", "password": "..." }
JWT payload returned via /auth/me
{ "role": "dev-engineer", "permissions": ["feature:read","feature:write","debug:access"] }
Revi AI checks permissions from the JWT. No second round-trip needed — permissions travel in the token.

Tenant users see their own account

Non-admin users (e.g., a developer in revi-dev) log in and land on the My Account page. They see their role, permissions, and tenant — but cannot access the admin console.

Screen: /account (auto-redirect for non-admins)  |  API: GET /api/v1/auth/me

Key APIs for Revi AI Integration

Auth Flow (Revi AI frontend → EMC Auth)

MethodEndpointHeaderWhen to call
POST/api/v1/auth/sessionX-Tenant-Slug: revi-devUser logs in — sets HttpOnly cookie
GET/api/v1/auth/meX-Tenant-Slug: revi-devOn app load — get user + permissions from cookie
POST/api/v1/auth/session/refreshX-Tenant-Slug: revi-devEvery 55 min — rotate access token before 1h expiry
POST/api/v1/auth/session/logoutX-Tenant-Slug: revi-devUser logs out — clears cookies

How Revi AI should integrate Set VITE_TENANT_SLUG=revi-dev (or revi-stage / revi-prod) in Revi's .env file. Every API call from Revi's axios client must include X-Tenant-Slug: revi-dev. EMC Auth then scopes all auth operations to that tenant automatically.

Quick curl — Test any tenant login

# Login to revi-dev
curl -X POST http://localhost:9090/api/v1/auth/session \
  -H "Content-Type: application/json" \
  -H "X-Tenant-Slug: revi-dev" \
  -d '{"email":"john@revi.ai","password":"..."}'
# Get user + permissions
curl http://localhost:9090/api/v1/auth/me \
  -H "X-Tenant-Slug: revi-dev" \
  --cookie "emc_access_token=<from login>"
