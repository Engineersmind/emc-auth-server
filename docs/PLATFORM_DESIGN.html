EMC Auth — Platform Design

Role hierarchy, authentication workflows, and API integration guide for the Auth0 replacement

1 — Role Hierarchy (3 Tiers)
Tier 1 · Platform

EMC Super Admin

Manages the entire auth platform — equivalent to Auth0 dashboard owner

  • 🏢 Create, manage and deactivate tenants
  • 👥 View all users across all tenants
  • 🔑 Manage system-wide permissions
  • 📊 View system audit logs
  • ⚙️ Configure SAML, CORS, rate limits
  • 🤖 Register agents (M2M auth)
  • 🔐 Issue management API tokens
Local login
Workspaceemc
Emailadmin@emc.local
PasswordChangeMe123!
Permissionstenant:manage + admin:access
Tier 2 · Tenant

Tenant Admin

Manages users and roles inside their own tenant — equivalent to Auth0 Application admin

  • 👤 Create and manage users in their tenant
  • 🛡️ Create roles and assign permissions
  • 📋 View tenant-scoped audit logs
  • 🔑 Create API keys for their tenant
  • 🔒 Force password resets
  • ❌ Cannot see other tenants
  • ❌ Cannot create tenants
Local logins (example: Outreach)
Workspaceoutreach
Emailadmin@outreach.local
PasswordDemo1234!
Permissionadmin:access
Tier 3 · End User

Application User

Users of applications that delegate auth to EMC — equivalent to Auth0 end users

  • 🔑 Login / logout to get JWT tokens
  • 👤 View and update their own profile
  • 🔐 Enroll in TOTP 2FA
  • 🔄 Refresh access tokens
  • 📱 Reset their own password
  • ❌ No admin panel access
  • ✅ Custom roles e.g. account_manager, viewer
Local logins (Outreach members)

4 — User Journeys

Journey 1 — Onboard a new application (Outreach)

1
EMC Super Admin creates the tenant
POST /admin/tenants → slug=outreach, name=Outreach
requires: tenant:manage
2
Super Admin defines permissions for Outreach
POST /admin/tenants/:tid/permissions → e.g. campaigns:read, campaigns:write, contacts:manage
requires: tenant:manage
3
Super Admin creates roles for Outreach
POST /admin/tenants/:tid/roles → admin (campaigns:*), account_manager (campaigns:read, contacts:manage), viewer (campaigns:read)
requires: tenant:manage
4
Super Admin creates the Outreach tenant admin user
POST /admin/tenants/:tid/users → admin@outreach.com, role=admin
requires: tenant:manage
5
Outreach Admin logs in and manages their own users
POST /auth/login (X-Tenant-Slug: outreach) → gets admin JWT → creates alice (account_manager), bob (viewer)
requires: admin:access
6
Outreach creates an API key for their backend service
POST /admin/api-keys → { name: "outreach-backend", permissions: ["admin:access"] }
returns: emck_xxx (save this!)

Journey 2 — End user authenticates in Outreach application

1
Alice (account_manager) logs into Outreach app
POST /auth/login → X-Tenant-Slug: outreach, email: alice@outreach.com
returns: access_token (JWT, 1hr) + refresh_token (30d)
2
Outreach app verifies Alice's identity and permissions
GET /auth/me → { user_id, email, role: "account_manager", permissions: ["campaigns:read","contacts:manage"] }
Outreach app gates features based on permissions[]
3
Token expires → Outreach app refreshes silently
POST /auth/refresh → { refresh_token } → new access_token
No re-login needed for 30 days
4
Alice logs out
POST /auth/logout → refresh token revoked, cookies cleared

Journey 3 — Outreach backend manages users programmatically (M2M)

1
Outreach backend exchanges API key for management token
POST /auth/management-token → X-API-Key: emck_xxx
returns: access_token (JWT, 15min) with admin:access
2
Backend creates a new user on signup
POST /admin/users → Authorization: Bearer <mgmt-token>, X-Tenant-Slug: outreach
{ email, password, role: "viewer" }
3
Token expires (15min) → backend re-exchanges API key
The API key (emck_xxx) is the long-lived credential. The JWT is always short-lived.
Same as Auth0's client_credentials grant
5 — API Quick Reference

🔑 Login (any user)

# Works for all 3 tiers
POST /api/v1/auth/login
X-Tenant-Slug: outreach

{
  "email":    "alice@outreach.local",
  "password": "Demo1234!"
}

# Response:
{
  "access_token":  "eyJ...",
  "refresh_token": "eyJ...",
  "permissions":   ["campaigns:read"]
}

👤 Verify identity

# Use in your app to gate features
GET /api/v1/auth/me
Authorization: Bearer eyJ...
X-Tenant-Slug: outreach

# Response:
{
  "user_id":     "uuid",
  "email":       "alice@outreach.local",
  "role":        "account_manager",
  "permissions": ["campaigns:read","contacts:manage"]
}

🤖 M2M management token

# Your backend uses this, not users
POST /api/v1/auth/management-token
X-API-Key: emck_xxxxxxxxxxxx

# Response:
{
  "access_token": "eyJ...",
  "expires_in":   900,
  "permissions":  ["admin:access"]
}

# Then use this JWT to manage users:
POST /api/v1/admin/users
Authorization: Bearer eyJ... (mgmt token)

🛡️ Role-based feature gating

# In your app backend (e.g. Node.js)

# 1. Verify JWT from EMC Auth
GET /api/v1/auth/me → permissions[]

# 2. Gate your endpoints
if (!permissions.includes('campaigns:write')) {
  return 403 Forbidden
}

# Custom permissions you define:
campaigns:read    → viewer
campaigns:write   → account_manager
contacts:manage   → account_manager
billing:access    → admin
