Application Roles & Feature Matrix

Complete role definitions, permissions, and feature access for every user type in the EMC Auth platform

🏛️ Platform-Level Roles (EMC Tenant)
Tier 1 · Platform
Super Admin
role: super_admin
tenant:manage + admin:access

Owns the entire auth platform. Creates and manages all tenants and their users.

  • ✅ Create / deactivate any tenant
  • ✅ View all users across all tenants
  • ✅ Manage permissions & roles for any tenant
  • ✅ View system-wide audit logs
  • ✅ Configure SAML, CORS, rate limits
  • ✅ Issue management API tokens
  • ✅ Register M2M agents
🏢 Tenant-Level Roles (e.g. Outreach, Senie, Acme)

These roles live inside a tenant. A Tenant Admin defines which permissions each role gets. The names below are recommended — they can be renamed to fit any application.

Tier 2 · Tenant
Tenant Admin
role: admin
admin:access

Manages everything inside their own tenant. Cannot see other tenants.

  • ✅ Create, edit, delete users in their tenant
  • ✅ Create and assign roles
  • ✅ Define custom permissions
  • ✅ View tenant audit logs
  • ✅ Create API keys
  • ✅ Force password resets
  • ❌ Cannot manage other tenants
Tier 2 · Tenant
Developer
role: developer
api:manage + users:read

Technical integration role. Can create API keys and access M2M tokens but cannot manage users.

  • ✅ Create and revoke API keys
  • ✅ Get management tokens (read scope)
  • ✅ View users (read-only)
  • ✅ View roles and permissions
  • ✅ View audit logs
  • ❌ Cannot create or delete users
  • ❌ Cannot assign roles
Tier 2 · Tenant
Account Manager
role: account_manager
users:write + contacts:manage

Manages client accounts. Can onboard and manage end users but cannot touch roles or system settings.

  • ✅ Create and manage end users
  • ✅ Assign end-user roles (member, viewer)
  • ✅ View user activity
  • ✅ App-specific: contacts:manage, deals:write
  • ❌ Cannot create roles or permissions
  • ❌ Cannot access API keys
  • ❌ Cannot view audit logs
Tier 2 · Tenant
Support Agent
role: support
users:read + password:reset

Handles user support tickets. Can look up users and trigger password resets. Read-only otherwise.

  • ✅ Look up users by email
  • ✅ Trigger password reset for a user
  • ✅ View user login history
  • ❌ Cannot create or delete users
  • ❌ Cannot change roles
  • ❌ Cannot see passwords or tokens
  • ❌ No API key access
Tier 2 · Tenant
Auditor
role: auditor
logs:read + users:read

Compliance and security review role. Read-only access to everything for reporting purposes.

  • ✅ View all audit logs
  • ✅ View all users (read-only)
  • ✅ View roles and permissions
  • ✅ Export reports
  • ❌ Cannot create or modify anything
  • ❌ No API key access
  • ❌ No user management
Tier 3 · End User
Member
role: member
auth only

Standard end user of the application. Can only authenticate and manage their own account.

  • ✅ Login and get JWT token
  • ✅ View their own profile
  • ✅ Reset their own password
  • ✅ Enroll TOTP 2FA
  • ✅ App-specific permissions (e.g. campaigns:read)
  • ❌ No admin panel access
  • ❌ Cannot see other users
Tier 3 · End User
Viewer
role: viewer
read-only app access

Restricted end user. Can only view content — no creation or editing in the app.

  • ✅ Login and get JWT token
  • ✅ View their own profile
  • ✅ App: read-only permissions only
  • ❌ No write permissions in app
  • ❌ No admin access

🔑 System Permissions (Built-in)

These permissions are created automatically by the seed and gate access to the admin API. Do not rename or delete them.

tenant:manage
Create, update, deactivate tenants. Super Admin only.
admin:access
Access all /admin/* endpoints for own tenant (users, roles, permissions, API keys, audit logs).

🚀 How to Set Up Roles for Your Application

Follow these steps as the Super Admin to fully configure a new tenant (e.g. Outreach) with all roles and users.

Step 1 — Create the tenant
POST /api/v1/admin/tenants
Authorization: Bearer <super-admin-jwt>
X-Tenant-Slug: emc

{ "name": "Outreach", "slug": "outreach" }
Step 2 — Create permissions for the tenant
POST /api/v1/admin/tenants/:tid/permissions
// repeat for each permission
{ "name": "campaigns:read",   "description": "View campaigns" }
{ "name": "campaigns:write",  "description": "Create/edit campaigns" }
{ "name": "contacts:manage",  "description": "Manage contacts" }
{ "name": "users:read",       "description": "View users" }
{ "name": "password:reset",   "description": "Reset user passwords" }
{ "name": "logs:read",        "description": "View audit logs" }
{ "name": "api:manage",       "description": "Manage API keys" }
Step 3 — Create roles and assign permissions
# 1. Create role
POST /api/v1/admin/tenants/:tid/roles
{ "name": "account_manager", "permission_ids": ["<campaigns:read>","<campaigns:write>","<contacts:manage>","<users:read>"] }

{ "name": "support",         "permission_ids": ["<users:read>","<password:reset>"] }

{ "name": "auditor",         "permission_ids": ["<users:read>","<logs:read>"] }

{ "name": "developer",       "permission_ids": ["<users:read>","<api:manage>"] }

{ "name": "viewer",          "permission_ids": ["<campaigns:read>"] }

{ "name": "member",          "permission_ids": ["<campaigns:read>","<contacts:read>"] }
Step 4 — Create users and assign roles
POST /api/v1/admin/tenants/:tid/users
{ "email": "alice@outreach.com", "password": "Temp1234!", "role": "account_manager", ... }
{ "email": "bob@outreach.com",   "password": "Temp1234!", "role": "support", ... }
{ "email": "dave@outreach.com",  "password": "Temp1234!", "role": "developer", ... }
{ "email": "jane@outreach.com",  "password": "Temp1234!", "role": "viewer", ... }
Step 5 — Your app verifies permissions on every request
# User logs in → gets JWT with their permissions embedded
GET /api/v1/auth/me → {
  "email": "alice@outreach.com",
  "role": "account_manager",
  "permissions": ["campaigns:read","campaigns:write","contacts:manage","users:read"]
}

# In your Outreach app backend:
if (!user.permissions.includes('campaigns:write')) {
  return 403  // alice can write, bob (support) cannot
}
